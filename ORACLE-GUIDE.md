# Step-by-step trace verification (oracles)

Goal: prove that EVERY STEP of every animation shows what the algorithm really holds at that moment — not only the final answer.
Method: for each problem write an INDEPENDENT simulator (the *oracle*) that records the algorithm's state after each semantic event;
`scripts/verify-traces.mts` runs the animation (`buildSteps`) on the declared examples + many random inputs, projects each step's
observable state, and requires the two traces to be equal, in order, modulo steps that change nothing observable.
Framework: `scripts/oracle/types.ts` (the `OracleCase` contract), `scripts/oracle/util.ts` (rng, `ptr`, `num`, `shown`, `cellValues`, `sceneOfKind`,
`scenesOf`), the runner `scripts/verify-traces.mts`, and a model case `scripts/oracle/cases-example.mts` (Fixed Sliding Window, LC 643) — copy its shape.
Run: `node scripts/verify-traces.mts` (all) · `ONLY=slug1,slug2 VERBOSE=1 node scripts/verify-traces.mts` · `RUNS=200 SEED=7 ...` for more random inputs · `LIST_UNCOVERED=1`.

## Rules that make the check meaningful
1. INDEPENDENCE. Write the oracle from the algorithm's definition in plain TypeScript. NEVER import the problem's own module, its kit (`stepKit`, `treeKit`, `listheapKit`, `primKit`, …) or copy its step-building code. If you read the animation file to learn WHAT it shows (vars names, aux titles, how pointers are labelled), that is fine for the PROJECTION, but the ORACLE must be derived from the textbook algorithm (you may look at the Java in `problem.java` as the spec). A bug present in both would otherwise go unseen.
2. STATE = what the viewer can see: `step.vars` (parse strings like `"[0..2]"`), pointers (`ptr(step,'l')`), array cell values/order (`cellValues`), aux panel items (stack/queue/map/list), scene nodes (tree/ntree/graph/trie labels, states), grid cells (DP table). Project the data structures that matter for THIS algorithm (the stack, the DP table, the distance array, the heap, the queue, the sorted prefix, …) plus the key variables. At least 2 meaningful keys per problem; a projection that only echoes one scalar proves little.
3. GRANULARITY. The oracle emits one state per semantic event in the order the algorithm performs them (include the initial and final states). The animation may show several steps per event (compare, then update): steps that do not change the projected state collapse automatically. If the animation updates two variables in two separate steps, either project only keys that change together, or let the oracle emit the intermediate state too (legitimate when the algorithm's own sequential assignments produce it). Do NOT loosen a projection merely to make a mismatch disappear.
4. INPUTS. `gen(r)` returns a valid random input of the same shape as `examples[].input` (see `problem.examples[0].input`, the parser/validation inside the problem, and the generators in `scripts/fuzz-*.mts`, which you may reuse). Respect the animation size caps (graph ≤ 12 nodes, trees ≤ 40, strings/arrays small). The runner always also runs every declared example. Include edge cases in `gen` (empty-ish, size 1, duplicates, ties, negative numbers, disconnected graphs, unreachable targets) with some probability.
5. WHEN A CASE FAILS decide which side is wrong: (a) the ANIMATION is wrong (wrong pointer, wrong number, wrong order, missing event, wrong tie-breaking vs the standard algorithm) → fix the problem file with a minimal Edit, keep input/output contracts, slugs, and keep its `scripts/fuzz-*.mts` passing; (b) the ORACLE is wrong → fix it; (c) both are valid but differ by an explicit, documented design choice (e.g. a different but correct tie rule shown consistently, or an extra pedagogical state) → document it in the case's `notes` and align the oracle to the design only if the animation is consistent with the algorithm's definition. Never silence a real animation bug. Record EVERY real animation bug you fix (problem, example input, step, what was wrong) in `scripts/oracle/FINDINGS-<batch>.md`.
6. `invariants` (optional but encouraged): rules that must hold at every step, e.g. window sum equals the sum of the framed cells; a monotonic stack stays monotonic; heap property; BST ordering; a sort array is a permutation of the input; settled Dijkstra distances never change; union-find parents are acyclic.
7. HONESTY: use `notes` to say what a case does NOT verify (e.g. "scene colours not checked", "only the dp row is compared").
8. Work incrementally so a stall loses little: write the cases file in chunks of ~6–8 problems, run `ONLY=<those slugs>` after each chunk, fix, continue. Your cases file is `scripts/oracle/cases-<batch>.mts` (one file per batch; no other agent edits it). Do not edit the runner, `types.ts`, `util.ts` or other batches' files — if you need a helper, define it at the top of your own file (or tell the lead what to add to `util.ts`).
