## Data model (already wired; do not edit the shared files)
- A **pack** = `src/data/packs/pN.ts` exporting `pack: PatternPack` (types in `src/data/packs/types.ts` — read it). You own exactly one pack file and one problem group file `src/problems/groups/packN.ts` (exports `packN: AnyProblem[]`; already imported by `registry.ts`). Merged automatically into: the catalog (`pack.problems` → new catalog entries, slug `<id lowercased>-<slugified title>`; new categories allowed), the pattern list (`pack.groups` → new cards, new families allowed), `CONTENT` (`pack.content` for NEW patterns), `PATTERN_META` (`pack.meta` for NEW patterns) and the examples (`pack.examples[slug]` for EXISTING and NEW patterns; read via `examplesFor(slug)` in `src/data/patterns.ts`).
- **Examples rule (enforced by `EXAMPLES_STRICT=1 npm run check`)**: every pattern has **at least 3 different animated problems** in `pack.examples[slug]`; the **first must equal the pattern's `animation`** (the existing flagship for the 44 old patterns; for a new pattern set `content.animation` to your first example); every example has a `why` of ≥ 20 characters. "Different altogether" means: a different problem **and** a different angle — different data shape or constraint, a variation in how the pattern is applied, or a different failure/edge it teaches (e.g. fixed window: *max average* (running sum) → *permutation in string* (window of counts) → *sliding window maximum* (the window needs a deque)). Do not pick three near-duplicates. Prefer problems that are **already animated** in the catalog (the 188 + other packs) when they fit; build new animations when the catalog lacks a good fit. Every example's problem must be registered/animated by the end.
- **New problems**: add them to `pack.problems` (id/title/difficulty/tag/category) AND implement `ProblemDef`s in your problem files (slug must equal the catalog slug; difficulty/category must match; `npm run check` enforces it). Use the real LeetCode number when the problem exists on LeetCode; for classic algorithm demos without a LeetCode number use id `CP` (classic/competitive) or `ALG` (algorithm demo) or `GFG`. **Before adding a problem, check it isn't already in the catalog** (`src/data/catalog.ts`, other packs' `problems`, e.g. `Select-String`/Grep for the title). If two packs collide, the check fails on duplicate slugs — the later agent removes its duplicate and reuses the existing slug.
- **New patterns** need: a card (`pack.groups`: slug|title|tags|complexity), content (`pack.content`: `animation`, `summary`, `whenToUse` ≥ 3 bullets, `tip`, `template` — a commented, compilable-looking Java template —, `practice` ≥ 3 rows: catalog slugs, `{slug, note}` or external `PracticeItem`s with accurate LeetCode id/title/difficulty/URL — only problems you are sure about) and meta (`pack.meta`: `icon`, `label`, `desc`, `useNote`, `complexityNote`, `highlight` words) — see existing entries in `src/data/patterns.ts`, `src/data/patternContent.ts`, `src/data/patternMeta.ts` for depth and tone. Own wording everywhere.
- Scenes available: array/bars, list, tree (new: optional `extraEdges` dashed arrows between node ids, e.g. threads/jumps), grid/table, graph, intervals, trie, split, plus `aux` panels (stack/queue/map/list). Only agent **p9** may add scene kinds or touch `types.ts`/`SceneView`/renderers; everyone else uses what exists (labels, aux panels, tags) and notes any visual limitation in the report.
- Quality bar is the same as the 188: reference-solution fuzz (`scripts/fuzz-packN.mts`, ~200 random inputs per problem, compare final answers), `npm run check` structural checks, ≤ 400 steps, friendly `parseInput`, input caps for readability, Java + Python code with correct highlighted lines, `approach/algorithm/complexity/why`. For problems that are really *algorithm demos* (KMP, Fenwick, …) animate the real algorithm's internal state (failure table, tree nodes, …).
- Work order: (1) the examples for your **existing** patterns (reuse animated catalog problems where they fit, build new ones where they don't), (2) your **new** patterns (flagship first). Finish and verify what you do rather than leaving half-done files. If you run low, report precisely what is left.
